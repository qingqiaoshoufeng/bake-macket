# 烘焙商城首期设计规格

- **日期：** 2026-07-12
- **状态：** 已获设计确认，待用户审阅
- **范围：** H5 顾客商城、PC 商家商品管理后台、微信小程序 H5 容器、NestJS 后端

## 1. 目标与首期边界

建设一个单商家烘焙商城，完成“商家维护商品和库存 → 顾客浏览并下单 → 商家处理订单”的业务闭环。

首期明确包含：

- H5 商品浏览、商品详情、SKU 选择、购物车、结算、订单、地址簿和个人资料。
- PC 商家后台的管理员登录、分类、商品/SKU/库存、商品图片、富文本详情、Banner 和订单状态处理。
- 原生微信小程序作为 `web-view` H5 容器，并桥接微信登录；启动时自动登录是快捷路径，H5 登录页同时提供显式微信登录按钮，经同源校验的原生页面取得一次性 `wx.login` code 后以内存 handoff 交回 H5。
- NestJS 后端统一提供用户端、后台和上传接口。
- 小程序内可自动完成微信授权登录；普通浏览器使用模拟手机号验证码。顾客在“我的”维护非唯一的订单联系手机号，结算只提交其版本，后端在订单事务内锁定 User 并冻结服务端号码快照。顾客购物和 OPERATOR 管理均不依赖收费的 `getPhoneNumber` 能力。
- 到店自提和同城配送两种履约方式。

首期明确不包含：

- 微信支付、支付状态机、退款、支付回调或对账。
- 配送费、满额免配送费、距离/区域计费。
- 取消订单后的自动库存回补。
- 员工账号、角色权限、管理员自助注册或找回密码。
- 多门店、多商家、多级分类、场景导购的实际运营配置。
- 自提时段、营业日或每日产能校验。
- 生产可用的真实短信验证码服务（后续接入腾讯云短信）。
- Nuxt 或任何服务端渲染（SSR）。

## 2. 技术架构

采用 pnpm workspace Monorepo。前端为客户端单页应用（SPA），各应用独立构建与部署。

```text
bake-mall/
├── apps/
│   ├── h5-store/          # Vue 3 + Vite + TypeScript + Vant 4
│   ├── admin-web/         # Vue 3 + Vite + TypeScript + Element Plus
│   ├── miniapp-shell/     # 原生微信小程序
│   └── api/               # NestJS + TypeScript
├── packages/
│   └── shared-contracts/  # API DTO、枚举、共享类型；不包含业务实现
├── infra/                 # Docker、部署与环境变量样例
└── docs/
```

运行时依赖：

```text
小程序 web-view ─┐
微信浏览器 ──────┼─> H5 商城 SPA / CDN ──HTTPS──> NestJS API ─> MySQL
普通浏览器 ──────┘                                  ├──────────> 腾讯云 COS/CDN
商家后台 SPA / CDN ───────────────────────────────────└──────────> 微信/短信服务
```

- H5 商城与后台均为静态资源，部署至 CDN 或静态站点服务。
- NestJS API 容器化部署，通过 HTTPS 对外提供服务并连接托管 MySQL。
- 图片二进制存放腾讯云 COS；MySQL 只保存对象键、访问 URL、排序和关联元数据。
- `shared-contracts` 仅承担前后端契约同步，不允许导入任一应用的业务服务。

## 3. 用户身份与会话

| 入口 | 身份获取 | 统一结果 |
|---|---|---|
| 小程序内 H5 | 小程序原生获得微信 `code`，经安全桥接交给 H5/后端，并由应用级协调器自动兑换 | 商城用户会话 |
| 微信浏览器 H5 | 网页微信 OAuth | 商城用户会话 |
| 普通浏览器 H5 | 手机号 + 开发/联调模拟验证码 | 商城用户会话 |
| 商家后台 | 唯一超级管理员的账号 + 密码 | 管理员会话 |

后端使用微信 OpenID/UnionID（可获得时）与历史已验证身份手机号将身份归一至同一个用户。手机号分为三个互不替代的域：`User.phone` 是唯一的历史身份手机号；`User.orderContactPhone` 是非唯一的履约资料，带独立 `version`；`AdminUser.loginPhone` 是唯一的 OPERATOR PC 登录手机号。订单联系号不触发身份归一、不进入 JWT、不改变 `tokenVersion`，也不代表号码已验证。OPERATOR 资格只要求 linked User 存在、active、未合并并具有微信 OpenID 或 UnionID；会员若继续使用微信手机号验证，则是与购物、履约和管理员授权分离的独立能力。

用户会话与管理员会话必须隔离：

- 使用不同的登录接口、JWT 密钥、`audience` 声明和 NestJS 守卫。
- H5 与后台分别存放各自令牌，严禁令牌混用。
- 管理员初始账号和密码通过环境变量或部署初始化脚本提供，不写入代码、迁移文件或 Git。

| 结算 | 登录前置校验；展示服务端订单联系号脱敏值与修改入口；提交联系号版本；自提或配送选择；订单备注；提交订单 |
| 订单 | 我的订单列表和订单详情；展示履约与订单状态快照 |

### 4.2 H5 视觉与组件

- 使用 **Vant 4**，移动端采用“小清新”风格。
- 色彩基调为奶油白、浅草绿与暖杏色；使用大圆角、轻柔阴影和清晰的商品图片层级。
- 首页采用商品优先的信息架构：Banner → 分类入口 → 人气商品双列流 → 底部导航。
- 场景导购（生日、下午茶、早餐、礼赠）预留为未来可配置内容位，不改变商品分类和订单模型。
- 交互必须保持 Vant 的移动端可用性：表单校验、加载、错误与禁用状态清晰可见，关键状态不得只靠颜色传达。

## 6. 核心领域模型

```text
User ──< Address
User ──< CartItem >── Sku ──> Product ──> Category
User ──< Order ──< OrderItem
Product ──< Sku
Product ──< ProductImage
Banner ──> Product 或 Category（可选跳转）
AdminUser（SUPER_ADMIN 或显式授权的 OPERATOR）
AdminUser ──< AuditLog
```

| 实体 | 关键字段/责任 | 约束 |
|---|---|---|
| `User` | 微信身份、头像昵称、可选历史身份手机号、非唯一订单联系手机号及版本 | `phone` 仅用于历史身份归一；`orderContactPhone` 仅用于履约，不回写身份、不参与管理员资格 |
| `AdminUser` | SUPER_ADMIN 邮箱身份，或 OPERATOR 的唯一 `loginPhone`、`linkedUserId`、角色与 token version | 仅 SUPER_ADMIN 可显式授权/撤权；OPERATOR linked User 必须具有微信 OpenID/UnionID |
| `Address` | 收货人、手机号、省市区、详细地址、默认标记 | 每用户最多一个默认地址；地址手机号不作为订单联系号 fallback |
| `Category` | 名称、图标/图片、排序、启用状态 | 仅单层分类 |
| `Product` | 名称、简介、分类、详情 HTML、上架状态 | 不存售价和库存；只负责展示信息 |
| `Sku` | 规格属性、售价（分）、库存、可选图片、状态 | 库存必须非负；价格与库存均以 SKU 为准 |
| `CartItem` | 用户、SKU、数量 | 引用实时 SKU；失效项在结算前提示 |
| `Order` | 编号、状态、履约方式、商品总额（分）、备注、履约快照 | 创建后核心成交内容不可编辑 |
| `OrderItem` | 商品/SKU 名称、规格、图片、成交单价（分）、数量 | 完整快照，不依赖实时商品数据 |
| `Banner` | 图片键/URL、标题、目标类型、目标 ID、排序、状态 | 用户端仅显示上架且目标有效的 Banner |
| `AuditLog` | 管理员、时间、对象、动作、变更摘要 | 用于后台关键操作追溯 |

所有金额均以整数**分**持久化、传输和计算，禁止使用浮点数。

## 7. 商品、SKU、库存与购物车

- 商品必须支持多规格 SKU，例如尺寸、口味等组合；每个 SKU 独立维护售价、库存和上架状态。
- 顾客在详情页选择 SKU 并加入购物车；SKU 无库存或下架时不可加入。
- 后台可直接维护 SKU 库存；后台编辑不改写历史订单。
- 购物车只保存实时 SKU 引用，不能作为成交历史依据。
- 下单时由后端权威校验实际 SKU 状态、售价和库存；前端展示库存仅作体验提示。

## 8. 订单与履约

### 8.1 创建订单

从购物车结算创建订单。订单总额仅为所有 `SKU 成交单价 × 数量` 的总和；首期没有支付金额、配送费、优惠、运费或税费。

创建订单时，后端必须在单一 MySQL 事务内：

1. 已完成幂等记录先返回其不可变响应快照，不因当前资料变化而拒绝 replay；
2. 按统一锁序锁定当前 User，确认 active、未合并、订单联系号已配置且客户端版本仍匹配；完整联系号只能从该服务端锁定行读取；
3. 校验购物车项、SKU 状态和购买数量；
4. 对每个 SKU 执行“库存不少于数量才扣减”的条件更新；
5. 任一 SKU 扣减失败则整体回滚，并返回失败 SKU 明细；
6. 生成唯一订单号，写入订单、订单项和服务端订单联系号等全部必要快照；
7. 清除本次成功结算的购物车项并完成幂等快照；
8. 提交事务。

创建订单接口要求客户端传递 `Idempotency-Key`。同一用户以相同键重复请求时，后端返回第一次创建的订单，不得重复创建或重复扣库存。

### 8.2 履约方式

| 履约方式 | 顾客输入 | 订单快照 |
|---|---|---|
| 到店自提 | 联系人、自由文本的期望取货时间；联系号来自个人资料 | 联系姓名、服务端联系号和原始取货时间文本 |
| 同城配送 | 联系人、配送地址；可使用地址簿；联系号来自个人资料 | 联系姓名、服务端联系号、完整地址与“由商家联系确认配送时间”的说明 |

自提自由文本不校验营业日、营业时间、可用时段或产能。配送首期不计算配送费，商家负责后续联系确认。

### 8.3 状态机

```text
NEW（新订单） → PROCESSING（处理中） → COMPLETED（已完成）
                       └────────────→ CANCELLED（已取消）
```

- 创建订单后为 `NEW`，库存已扣减。
- 管理员只能按该图执行状态流转；后端拒绝反向、跳过或终态后的任何流转。
- 管理员只能查看订单和更新状态，不得编辑订单商品、SKU、数量、价格、联系人或履约快照。
- 取消订单首期**不自动回补库存**；后台需明确提示管理员这一规则。
- 顾客订单备注可保存并供后台查看，但不改变 SKU、金额或库存。

## 9. API 边界

后端使用版本化 REST API：`/api/v1`。

```text
/public/*       # Banner、分类、商品与 SKU 展示
/auth/*         # 用户微信授权、验证码、手机号绑定
/me/*           # 用户资料、订单联系号及版本、地址、购物车、我的订单
/orders         # 创建订单；要求登录，只提交订单联系号版本，服务端冻结完整号码快照
/admin/auth/*   # SUPER_ADMIN 邮箱登录、OPERATOR 独立 loginPhone 登录与微信 linked User 会话兑换
/admin/*        # 分类、商品、SKU、Banner、订单和审计日志
/upload/*       # 管理员请求 COS 上传签名/上传协调
```

接口错误约定：

| 场景 | 状态码与响应 | 客户端处理 |
|---|---|---|
| 商品订单未登录 | `401` + 业务码 | 等待小程序自动登录，或通过显式原生微信登录 handoff 后返回原结算步骤 |
| 订单联系号缺失或版本变化 | `409` + 稳定业务码 | 前往“我的”设置，或刷新脱敏值后以新幂等键重新确认 |
| 会员独立能力手机号未验证 | `403` + `PHONE_REQUIRED` | 仅在该会员能力保留时引导受信任手机号验证；购物和 OPERATOR 不依赖此门槛 |
| 库存不足、SKU 下架 | `409` + SKU 明细 | 标记购物车失效项，提示调整并重试 |
| 相同幂等键重试 | 返回首次订单 | 进入该订单详情，不重复扣库存 |
| 非法订单状态流转 | `422` | 后台显示操作不可执行原因 |
| COS 上传失败 | 可重试错误 + 请求 ID | 保留表单内容，允许重试上传 |
| 未处理服务异常 | `500` + 请求 ID | 统一错误提示；日志记录完整上下文且不泄露堆栈 |

## 10. 图片上传与富文本安全

- 管理员上传商品和 Banner 图片前，后端签发一次性、短有效期的 COS 上传凭证，或通过受控上传接口协调上传。
- 后端限制图片对象路径、上传类型、MIME 类型、文件大小和管理员权限；上传失败可安全重试。
- 商品和 Banner 只持久化 COS 对象键、访问 URL 和展示元数据，禁止将图片二进制写入 MySQL。
- 商品富文本由后台编辑器提交；后端必须按 HTML 白名单清洗。
- 允许基础排版、受控链接与 COS 图片；移除脚本、事件处理器、危险 URL 和其他可执行内容。
- H5 只渲染服务端清洗后的内容，禁止执行富文本中的任何脚本。

## 11. 质量、测试与验收

### 11.1 测试层级

- **后端单元测试：** 金额计算、订单状态机、条件库存扣减、幂等逻辑、订单号和 HTML 清洗。
- **后端集成测试：** MySQL 事务与并发抢库存、权限隔离、订单快照、COS 签名权限。
- **前端测试：** SKU 选择、购物车汇总、履约表单校验、订单状态显示。
- **端到端测试：** 管理员创建分类/商品/SKU/Banner → H5 浏览和加购 → 小程序自动或显式微信登录 → “我的”保存订单联系号 → 结算确认脱敏值 → 自提/配送下单 → 后台更新订单状态。
- **小程序联调：** 合法业务域名和 `web-view` 域名、同源原生登录页、一次性 code 内存 handoff、URL 凭证清理与会话恢复；OPERATOR 直接以微信 linked User 资格换取管理会话，不进入 `flow=admin` 手机号授权。

### 11.2 首期验收条件

1. 管理员可登录、创建单层分类，上传商品图，创建带多个 SKU 的上架商品，并维护库存。
2. H5 首页能展示上架 Banner、分类和可售商品；用户可搜索并浏览详情富文本。
3. 用户可选择 SKU 并维护购物车；无库存或下架 SKU 不能成功结算。
4. 小程序、微信浏览器和普通浏览器能走各自的身份入口；小程序支持自动登录和显式原生微信登录 handoff。商品下单前必须已在个人资料保存合法订单联系手机号，checkout 不接收完整号码，且资料修改不得改变历史身份手机号或验证状态。
5. 用户可使用自提或配送创建订单，填写订单备注；配送费始终为零且不展示收费规则。
6. 多次并发提交最后库存时，最多只有库存允许数量的订单成功，不得产生负库存或重复订单。
7. 历史订单始终展示创建时的商品、SKU、价格、联系人和履约快照，不受后续商品或地址修改影响。
8. 后台仅允许合法订单状态流转，且关键管理操作有审计记录。

## 12. 部署与环境基线

- API 使用 Docker 镜像部署，包含健康检查、HTTPS 配置和结构化日志。
- MySQL 使用托管实例，开启备份、私网访问与最小权限业务账号。
- COS 使用私有写入权限；通过 CDN 或自定义 HTTPS 域名提供受控公开读取。
- 使用 `dev`、`test`、`production` 环境变量隔离 MySQL、COS、微信与未来短信服务密钥。
- 小程序、H5、COS/CDN 和 API 的正式访问域名均必须为 HTTPS，并完整配置微信合法业务域名、`web-view` 域名和 COS/CDN 域名白名单。
- 0014 发布时将符合 11 位规则的历史 `User.phone` 回填为 `orderContactPhone`（version 1）；已有 OPERATOR 从 linked User 的合法历史身份手机号回填独立 `AdminUser.loginPhone`，无法回填者立即停用并递增 token version，须由 SUPER_ADMIN 重新授权。`down` 在发现新联系号、登录号或 legacy 停用状态时 fail closed。
- linked User 被停用、合并或失去全部微信 OpenID/UnionID，或 SUPER_ADMIN 撤权时，OPERATOR 的 exchange/guard 立即拒绝；撤权和密码安全事件递增 `AdminUser.tokenVersion`。订单联系号或历史身份手机号变化本身不影响管理员 token。
